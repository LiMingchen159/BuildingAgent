## 1. Status and code baseline

[knowledgeBase.ts](../../../../apps/api/src/agent/knowledgeBase.ts) resolves project KB/Repository directories under repository-root `data/**`, scans files recursively, and creates lightweight catalogs. [genericTools.ts](../../../../apps/api/src/agent/genericTools.ts) provides `read_file`, `search_files`, `write_file`, `patch`, and execution tools. [server.ts](../../../../apps/api/src/server.ts) exposes listing and Repository-file download routes.

The local directories and tool chain are **Implemented**. Automated upload/conversion, inherited ACLs, version history, malware scanning, and vector document retrieval are **Partial or Planned**. A file's presence in KB does not mean its content has been validated as a product fact.

## 2. Purpose and scope

Knowledge Base is project-provided reference and semantic/catalog input and is read-only to the Agent by default. Repository is a project work area and generated-artifact destination that tools may write. Neither is the Web application source repository, and neither should store API keys. `KB_CATALOG_SUMMARY.md` and `bms_guide.md` are routing guides, not live BMS value sources.

## 4. Normal data flow

1. `dataRoot` resolves `BUILDING_AGENT_DATA_DIR`/`DATA_DIR`, then creates `kb` and `repository` directories for the project id.
2. Every list request and Chat turn scans the corresponding directory recursively. Hidden entries are skipped, and at most 500 files are indexed.
3. Supported text extensions read the first 600 bytes and compact them to a 200-character excerpt. Other files contribute metadata and a kind only.
4. Runtime places a small sorted KB/Repository catalog in the system prompt. When the body is needed, the provider should call `read_file` rather than assume the excerpt is complete.
5. `read_file` and `search_files` cover both project KB and Repository and return scoped `kb:/` or `repo:/` paths.
6. `write_file` and `patch` are Repository-only. Generated artifacts should use `repository/outputs`. Execution tools run in Repository and receive KB, Repository, and output paths through environment variables.
7. `outputs/...` links in an assistant answer are merged with trusted tool downloads into structured download metadata; HTTP download repeats project authorization and path checks.

## 5. Data, state, and persistence

The defaults are `data/<projectId>/kb/**` and `data/<projectId>/repository/**`; `outputs/**` is a Repository subdirectory. Files in those directories are primary sources. `knowledgeBaseByProject` and `repositoryByProject` in `apps/data/store.json` are recent scan summaries plus some in-memory artifacts.

Repository listing merges disk entries with memory artifacts not already represented by id/path. Whether a file is rebuildable depends on its source: uploaded material is usually authoritative input, Agent outputs may need retention, and a catalog summary can be regenerated by scanning.

## 6. Authorization and project isolation

Listing and download require bearer, membership, selected project, and `chat:read`. Download rejects an empty path, absolute path, and any path containing `..`, then verifies that the resolved file remains in an allowed project Repository root. Agent file tools derive roots from non-model-controlled `context.projectId`; writes resolve only Repository-relative paths.

Baseline download reads also support an explicitly configured legacy data root and a small set of established locations, but containment is checked for each root. This is migration compatibility, not cross-project search.

## 7. Errors, degradation, and external dependencies

- A missing directory is created best-effort; scan/read failures return an empty result or skip an entry rather than stop the service.
- Binary files cannot be read as text through `read_file`; large files and returned line counts are bounded.
- `search_files` is recursive glob/substring search, not semantic retrieval, and returns at most 50 results.
- A missing download returns `404 repo_file_not_found`; an invalid path returns `400 repo_invalid_path`.
- Terminal/Python depend on host runtimes and packages. Successful file generation does not validate its content; domain verification is still required.

## 8. Extension points

A new ingestor should place the original in the correct project KB, preserve source/hash/time, and link transformations clearly to the original. A new readable format must bound size and parser resources; a new download root must keep resolve-and-containment checks. If vector retrieval is introduced, mark its index rebuildable and do not replace the source document. Generated artifacts should record source message/tool and verifiable fact provenance.

## 10. Known limitations and related documentation

- There is no separate REST upload, delete, or version API; an operational way to place files in a directory is not a stable product contract.
- Every Chat turn scans recursively. The file-count cap and large-directory performance require deployment evaluation.
- A text excerpt only covers the beginning and cannot replace full-text retrieval or PDF/DOCX parsing.
- Legacy Repository read compatibility makes deployment roots more complex; all new writes still use the current data root.
